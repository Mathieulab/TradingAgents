# Mathieu TradingAgents Project Audit

Audit date: 2026-06-16

Scope: first-pass audit plus additive finance-lab planning. No TradingAgents business logic was changed for this audit.

## 1. Current Project Architecture

TradingAgents is a Python package with an interactive CLI and a LangGraph-based multi-agent workflow.

- `cli/`: Typer/Rich/questionary CLI, interactive prompts, live progress display, report saving, and token/tool stats.
- `tradingagents/`: core package.
- `tradingagents/graph/`: graph orchestration, workflow setup, propagation, checkpoints, reflection, conditional routing, and final signal parsing.
- `tradingagents/agents/`: analyst, researcher, trader, risk, and portfolio manager agents.
- `tradingagents/agents/utils/`: tool wrappers, graph state, memory log, structured-output helpers, rating parsing, and instrument context helpers.
- `tradingagents/dataflows/`: market/news/fundamental/macro/prediction-market data providers and routing.
- `tradingagents/llm_clients/`: provider registry, model catalog, provider clients, API-key mapping, validation, and model capabilities.
- `tests/`: pytest coverage across providers, CLI utilities, dataflow routing, memory, checkpoints, structured agents, ticker handling, and stale-data guards.
- `scripts/`: focused smoke scripts, currently including structured-output smoke testing.
- `Dockerfile` and `docker-compose.yml`: containerized CLI paths with optional Ollama profile.

The main orchestration class is `TradingAgentsGraph` in `tradingagents/graph/trading_graph.py`. It configures dataflows, creates LLM clients, builds tool nodes, compiles the LangGraph workflow, runs analysis, writes JSON state logs, stores decisions in memory, and extracts the final rating.

The graph shape is built in `tradingagents/graph/setup.py`:

1. Selected analysts run first: market, sentiment, news, fundamentals.
2. Bull and bear researchers debate.
3. Research Manager produces an investment plan.
4. Trader produces a transaction proposal.
5. Aggressive, conservative, and neutral risk analysts debate.
6. Portfolio Manager produces the final decision.

## 2. How The CLI Works

The main command is:

```powershell
python -m cli.main
```

The installed command is:

```powershell
tradingagents
```

`cli/main.py` defines a Typer app with an `analyze` command. The CLI:

- shows a welcome panel and announcements,
- asks for ticker, date, output language, analysts, research depth, LLM provider, and model choices,
- allows several selections to be skipped through `TRADINGAGENTS_*` environment variables,
- auto-detects crypto-like tickers and removes fundamentals for crypto,
- builds a config from `DEFAULT_CONFIG`,
- instantiates `TradingAgentsGraph`,
- streams LangGraph chunks into a Rich live dashboard,
- writes per-section markdown reports while the run progresses,
- optionally saves a complete report after analysis.

Important output behavior:

- The current final decision is markdown prose from the Portfolio Manager.
- The final rating is parseable from the `**Rating**:` field generated by structured output.
- There is not yet a dedicated user-facing summary object with confidence, risk score, bullish/bearish lists, paper-trade suggestion, and disclaimer.

## 3. How LLM Providers Are Configured

Configuration starts in `tradingagents/default_config.py`. Key fields:

- `llm_provider`
- `deep_think_llm`
- `quick_think_llm`
- `backend_url`
- `temperature`
- provider-specific thinking fields:
  - `google_thinking_level`
  - `openai_reasoning_effort`
  - `anthropic_effort`

Environment overrides are centralized in `_ENV_OVERRIDES`:

- `TRADINGAGENTS_LLM_PROVIDER`
- `TRADINGAGENTS_DEEP_THINK_LLM`
- `TRADINGAGENTS_QUICK_THINK_LLM`
- `TRADINGAGENTS_LLM_BACKEND_URL`
- `TRADINGAGENTS_OUTPUT_LANGUAGE`
- `TRADINGAGENTS_MAX_DEBATE_ROUNDS`
- `TRADINGAGENTS_MAX_RISK_ROUNDS`
- `TRADINGAGENTS_CHECKPOINT_ENABLED`
- `TRADINGAGENTS_BENCHMARK_TICKER`
- `TRADINGAGENTS_TEMPERATURE`

`tradingagents/llm_clients/factory.py` creates provider clients. Native APIs are separated for Anthropic, Google, Azure, and Bedrock. The OpenAI-compatible family routes through `tradingagents/llm_clients/openai_client.py`.

The provider registry supports OpenAI, xAI, DeepSeek, Qwen, GLM, MiniMax, OpenRouter, Mistral, Kimi, Groq, NVIDIA NIM, Ollama, and generic OpenAI-compatible endpoints.

API-key env vars are centralized in `tradingagents/llm_clients/api_key_env.py`.

## 4. How Ollama And Local LLMs Are Configured

Ollama is treated as an OpenAI-compatible provider:

- provider key: `ollama`
- default base URL: `http://localhost:11434/v1`
- override env var: `OLLAMA_BASE_URL`
- API key: not required
- placeholder key sent to compatible client: `ollama`

The CLI includes Ollama in the provider menu and confirms the resolved endpoint.

For generic local servers such as vLLM, LM Studio, llama.cpp server, or a relay:

- provider key: `openai_compatible`
- `backend_url` is required
- API key is optional
- optional key env var: `OPENAI_COMPATIBLE_API_KEY`

Potential issue found: `docker-compose.yml` sets `LLM_PROVIDER=ollama` for `tradingagents-ollama`, but the project config currently listens for `TRADINGAGENTS_LLM_PROVIDER`. Unless another code path handles `LLM_PROVIDER`, that compose value may not affect the app.

## 5. How Memory Currently Works

There are two persistence systems.

Decision memory:

- Implemented by `TradingMemoryLog` in `tradingagents/agents/utils/memory.py`.
- Default path: `~/.tradingagents/memory/trading_memory.md`.
- Override: `TRADINGAGENTS_MEMORY_LOG_PATH`.
- At the end of a run, the final decision is appended as a pending markdown entry.
- On a later same-ticker run, pending entries are resolved by fetching post-decision returns.
- A short LLM reflection is generated and stored.
- Recent same-ticker and cross-ticker lessons are injected into the Portfolio Manager prompt.

Checkpoint resume:

- Implemented in `tradingagents/graph/checkpointer.py`.
- Opt-in through `--checkpoint` or `TRADINGAGENTS_CHECKPOINT_ENABLED`.
- Uses per-ticker SQLite checkpoint databases under `~/.tradingagents/cache/checkpoints/<TICKER>.db`.
- Checkpoints are cleared on successful completion.

Run logs:

- JSON state logs are written under the configured `results_dir`.
- CLI markdown report sections can be saved after analysis.

## 6. Existing Test Coverage

The project currently has 44 `test_*.py` files under `tests/`.

Test areas include:

- provider registry and API-key mapping,
- Ollama base URL handling,
- OpenAI-compatible endpoints,
- model validation and capabilities,
- temperature/env override behavior,
- structured agents and rendered markdown,
- memory log storage and reflection injection,
- checkpoint resume,
- data vendor routing and vendor errors,
- stale yfinance OHLCV guards,
- ticker normalization and safe path handling,
- CLI env skip paths,
- crypto asset mode,
- news lookahead and external data fallbacks.

`tests/conftest.py` injects placeholder API keys to prevent CI hangs and isolates dataflow config per test.

Gaps for the finance-lab goal:

- no dedicated backtesting metrics tests,
- no fake-trade ledger tests,
- no dashboard/report-generation tests,
- no structured final summary model for normal users,
- no tests for paper-trading profiles or learning loops yet.

## 7. Weak Points

- The first CLI attempt failed because dependencies were not installed in the active Python environment. After `python -m pip install -r requirements.txt`, `python -m cli.main --help` succeeds and the bare interactive command stays open for user input.
- The final user-facing output is still mostly long markdown. It is useful for researchers but hard for normal users to scan.
- The Portfolio Manager has a structured schema, but it does not expose confidence score, risk score, explicit bullish/bearish points, indicator summary, or paper-trade plan.
- There is no separated finance-lab workspace yet for project-specific MCP servers, skills, prompts, fake trading, notebooks, or dashboards.
- There is no local finance configuration file separate from upstream `DEFAULT_CONFIG`.
- Backtesting exists as a dependency (`backtrader`) but not as a clear first-class lab workflow in this repo.
- Paper trading is not a structured subsystem yet. The existing memory log stores decisions and later reflections, not trade lifecycle records.
- No canonical fake-trade schema, fake-trader personalities, or performance review loop exists yet.
- Visual reporting is limited to markdown and CLI display. No generated HTML/PNG/JSON report layer exists yet.
- Docker Ollama profile may use the wrong env var name (`LLM_PROVIDER` instead of `TRADINGAGENTS_LLM_PROVIDER`).
- External data can be live or rate-limited, so reproducibility remains limited even with fixed analysis dates.

## 8. Best Improvement Roadmap

Recommended incremental path:

1. Keep upstream-compatible code untouched while adding `finance_lab/` docs, config, skills, and MCP planning.
2. Add a structured final summary adapter that reads existing graph state and produces a stable JSON summary for users.
3. Add a finance-lab report generator that consumes saved state/data and emits HTML, PNG, and JSON summaries.
4. Add backtesting metrics with unit tests before adding complex strategies.
5. Add fake-trade storage with a schema, SQLite store, and paper-only trader profiles.
6. Add a learning/reflection loop for closed fake trades.
7. Add dashboards only after the data model is stable.
8. Add broker integration placeholders only when explicitly disabled by default and protected by config.
9. Consider real trading only after long paper-trading validation, risk controls, observability, and manual approval flows.

## 9. Risks Before Paper Trading

- The analysis may be persuasive but not measurable without a structured trade plan.
- Entry, exit, stop loss, take profit, fees, and slippage are not yet consistently captured.
- Current memory reflects final decisions, not complete trade lifecycle outcomes.
- The system needs deterministic metrics: total return, expectancy, drawdown, profit factor, win/loss size, fees impact, and slippage impact.
- Data quality and lookahead bias must be guarded for every backtest path.
- Users may over-trust LLM prose unless every output includes research-mode and not-financial-advice disclaimers.

## 10. Risks Before Real Trading

Real-money execution should not be added yet.

Before real trading, the project would need:

- explicit broker integration disabled by default,
- manual approval gates,
- order size caps,
- daily loss limits,
- kill switch,
- broker sandbox validation,
- audit logs,
- secret management,
- monitoring and alerting,
- reconciliation between intended and actual orders,
- compliance review,
- long paper-trading record across regimes.

Until those exist, the project should remain research, backtesting, and paper-trading only.
